| 项 | 内容 |
| --- | --- |
| 文档状态 | 核对稿。双方逐条确认后作为对接基线 |
| 提供方 | 黄石数公基平台 |
| 使用方 | 本系统 |
| 适用范围 | 库表分发、SFTP 文件传输 |
| 版本 | 0.2 |
| 日期 | 2026-11-22 |

本次只约定下面两种方式。消息队列通知、OGC 服务（WFS、WCS、WMTS）、线下光盘拷贝不在本文范围内；平台若另行提供，单独立项。

两种方式互相独立。同一数据集只选一种主方式，避免同一图层同时走库表和文件、两边各更新一版。

## 1. 库表分发

平台主库有数据变更后，由平台把数据写入本方提供的库，并按双方确认的建表语句自动建表。本方不直接连平台主库。

数据“已经更新”以表内字段为准。本方用定时任务按水位读取变更行。平台完成写库，即完成投递；不依赖平台再调用本方程序。

### 1.1 库与账号

- 使用方提供独立的对接库，与业务库分开。平台只访问对接库。
- 平台账号具备约定表的插入、更新权限。删除业务行不授权，删除语义见 1.3。
- 建表、加列、改类型走 1.6 的结构变更，不在日常同步里直接改表。
- 库字符集使用 UTF-8。
- 时间一律用北京时间（UTC+8），精度到毫秒。双方服务器开启自动对时。

具体数据库产品（达梦、人大金仓、MySQL、PostgreSQL 等）以环境为准。下面给出的是字段语义，落地时按该产品的类型书写建表语句，语义保持不变。

### 1.2 业务表必带字段

每张参与分发的业务表，除业务字段外固定带以下字段。字段名若平台已有统一命名，可以改名，语义按下表执行，并在第 4 节核对表中写明实际字段名。

| 建议字段名 | 语义 | 规则 |
| --- | --- | --- |
| 业务主键 | 行的稳定身份 | 非空，有唯一索引。一经发布不复用、不修改 |
| `jhpt_update_time` | 该行最后一次业务变更时间 | 新增、修改、删除标记时都刷新为当时系统时间。精度毫秒 |
| `jhpt_update_status` | 变更类型 | `I` 新增，`U` 修改，`D` 删除。长度 1 的字符 |

字段要求：

- 平台在插入时写 `I` 和当前时间。
- 平台在修改业务字段时写 `U`，并刷新 `jhpt_update_time`。
- 业务字段没有变化时，不刷新 `jhpt_update_time`，避免本方重复处理。
- 每张表提供中文字段注释，注释与资源目录的信息项一致。
- 建表语句、主键、索引、字段中文名作为该表的冻结附件，随版本保存。

空间数据若走库表，几何字段的存储形态（数据库几何类型、WKT 或 WKB）和坐标系在第 4 节按表确认。建议坐标系为 CGCS2000，EPSG:4490。几何字段与坐标系必须写进建表说明。

### 1.3 删除

删除保留源行，把 `jhpt_update_status` 更新为 `D`，并刷新 `jhpt_update_time`。

平台不对业务表做物理删除。物理删除后，本方按时间水位扫描不到这一行，业务库会继续保留已失效数据。

本方读到 `D` 后，在业务库做逻辑删除，不把对接库里的这一行删掉。

### 1.4 增量读取

- 每个数据集首次下发为全量，之后为增量。
- 本方为每张表在**业务库**保存水位，内容是已成功处理到的 `jhpt_update_time` 和业务主键。水位不放在平台会覆盖的对接表里。
- 读取条件：`jhpt_update_time` 大于已保存时间；时间相等时，业务主键大于已保存主键。
- 排序固定为 `jhpt_update_time`、业务主键，分页读取。同一毫秒有多行时，只记时间会漏行或重复扫。
- 本方整页处理成功后才推进水位。中途失败则本页重试，水位不动。
- 按业务主键幂等写入。同一主键重复推送，业务库只保留一份。

平台全量重灌时，在对账表中把该批次标为全量（见 1.5），本方以该批次覆盖业务库中的对应表。未通过对账表声明的清空、重建，本方不把它当作正式全量。

### 1.5 批次对账表

平台每完成一次对某张表的下发，向对接库写入对账表一行。本方靠这行得知“这一批已经写完”，再按 1.4 处理该时间窗内的变更。

建议表名：`t_exchange_batch`

| 字段 | 写入方 | 语义 |
| --- | --- | --- |
| `batch_id` | 平台 | 批次号，全局唯一 |
| `table_name` | 平台 | 业务表名 |
| `load_type` | 平台 | `F` 全量，`C` 增量 |
| `row_count` | 平台 | 本批写入或更新的行数 |
| `window_start` | 平台 | 本批对应的起始时间，增量可空 |
| `window_end` | 平台 | 本批数据中的最大 `jhpt_update_time` |
| `exchange_time` | 平台 | 平台写完本批的时间 |
| `consume_status` | 本方 | `0` 待处理，`1` 成功，`2` 失败 |
| `consume_time` | 本方 | 本方处理完成时间 |
| `consume_count` | 本方 | 本方实际处理行数 |
| `consume_remark` | 本方 | 失败原因或差异说明 |

规则：

- 平台插入时 `consume_status` 置 `0`。
- 本方只更新消费四个字段，不改平台写入的批次字段。
- 本方处理行数与 `row_count` 不一致时，`consume_status` 置 `2`，并在 `consume_remark` 写明差异。双方按批次重传，不按零散行口头补数。
- 更新消费字段时，不修改业务表的 `jhpt_update_time`。

没有对账表时，本方仍可按 1.4 的时间水位轮询。对账表用来确认一批已经写完、以及双方条数一致。建议与水位同时启用。是否建表，在第 4 节确认。

### 1.6 结构变更

新增表、加列、改类型、改主键、改几何类型、改坐标系，按下面的顺序做：

1. 平台把变更后的建表说明发给本方。
2. 本方确认可以接收。
3. 平台执行变更。
4. 平台按全量批次重新下发该表，并在对账表标明 `F`。

日常同步过程中不改变已发布的表结构。

### 1.7 一条变更在表里的样子

下面只说明字段语义，业务列按实际表替换。

| biz_id | name | jhpt_update_time | jhpt_update_status |
| --- | --- | --- | --- |
| 1001 | 某某路 | 2026-11-22 02:00:00.000 | I |
| 1001 | 某某路（更名） | 2026-11-22 09:30:00.128 | U |
| 1001 | 某某路（更名） | 2026-11-23 08:00:00.000 | D |

本方水位若停在 `2026-11-22 02:00:00.000` / `1001`，下一轮会读到后两行，先更新名称，再逻辑删除。

## 2. SFTP 文件传输

适用于 SHP、GeoTIFF 等以文件交付的数据。传输协议使用 SFTP，按二进制传输。

文件内容是否完整，用 32 位十六进制 MD5 核对。MD5 是公开算法，与编程语言无关。平台用任何语言或命令算出的 32 位十六进制指纹，本方 Java 程序都可以复核。

### 2.1 账号与目录

每个数据集使用独立目录。建议结构：

```text
/{数据集编码}/incoming/    平台上传区，本方只读
/{数据集编码}/receipt/     本方回执区，本方写、平台读
```

- 平台把文件写入 `incoming`。本方不在 `incoming` 里移动、改名或删除文件。
- 本方用业务库中的处理台账记录已成功处理的「文件名 + MD5」。同一文件名且同一 MD5 只入库一次。
- 平台按保留周期清理 `incoming` 里已经回执成功的文件。保留周期在第 4 节确认，建议不少于 30 天。
- 账号按数据集授权到对应目录。密码、私钥不写入本文档。

### 2.2 一次投递的三个文件

一个图层一次投递对应三个文件，文件名主体相同，按下面的顺序上传：

1. 数据包：`{名称}_{装载}_{周期}_{日期}_{时间}.zip`
2. 清单：同名，后缀 `.manifest.txt`
3. 完成标志：同名，后缀 `.ok`。空文件，最后上传

本方只有同时看到 zip、清单和 `.ok` 才开始处理。`.ok` 表示 zip 和清单都已传完。

命名规则：

| 段 | 取值 | 说明 |
| --- | --- | --- |
| 名称 | 图层或数据集名称 | 双方登记的稳定名称，不含空格 |
| 装载 | `F` 或 `C` | `F` 全量，`C` 增量 |
| 周期 | `D` `W` `M` `Q` `H` `Y` `R` | 日、周、月、季、半年、年、按更新即传 |
| 日期 | `yyyyMMdd` | 数据日期，8 位 |
| 时间 | `HHmmss` | 24 小时制，6 位，北京时间 |

示例：

```text
道路_F_D_20261122_020000.zip
道路_F_D_20261122_020000.manifest.txt
道路_F_D_20261122_020000.ok
```

重传使用新的时间，不覆盖尚未回执的旧包。

一个 zip 只放一个图层。多个图层分多个包投递。

### 2.3 压缩包内容

zip 内使用 UTF-8 路径，目录固定为两级：

```text
空间数据/     图层文件
数据说明/     元数据、数据字典、范围说明
```

SHP 必须成套放入 `空间数据`，同一图层的主文件名相同：

```text
空间数据/道路.shp
空间数据/道路.shx
空间数据/道路.dbf
空间数据/道路.prj
空间数据/道路.cpg
数据说明/元数据.txt
数据说明/数据字典.txt
```

- `.prj` 记录坐标系，且与清单中的 `crs` 一致。
- `.cpg` 记录属性表字符集。建议 UTF-8。若为 GBK，`.cpg` 内容写 `GBK`，清单中 `charset` 同样写 `GBK`。
- GeoTIFF 放入 `空间数据`，坐标系写在影像自身和清单 `crs` 中，两处一致。
- DEM 高程放的是这一期、该图层约定范围内的完整高程格网。一次投递覆盖该范围的全部高程。

`数据说明` 至少包括：数据名称、提供单位、数据日期、坐标系、覆盖范围、字段含义。

### 2.4 清单与 MD5

清单是 UTF-8 文本，一行一个 `键=值`，与具体编程语言无关。Java 与其他语言按行读取即可。

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `file_name` | 是 | zip 文件名，与实际文件名一致 |
| `file_size` | 是 | zip 的字节数 |
| `md5` | 是 | zip 文件内容的 MD5，32 位十六进制 |
| `dataset_code` | 是 | 数据集编码，与目录名一致 |
| `layer_name` | 是 | 图层名称 |
| `load_type` | 是 | `F` 或 `C`，与文件名中的装载标记一致 |
| `crs` | 是 | 坐标系，如 `EPSG:4490` |
| `charset` | 矢量必填 | 属性表字符集，如 `UTF-8`、`GBK` |
| `feature_count` | 矢量必填 | 要素条数。栅格填 `0`，并在 `remark` 说明 |
| `data_time` | 是 | 数据日期，`yyyyMMdd` |
| `increment_mode` | 增量为必填 | `UPSERT`、`DELETE` 或 `MIXED`。全量留空 |
| `remark` | 否 | 补充说明 |

清单示例：

```text
file_name=道路_F_D_20261122_020000.zip
file_size=1048576
md5=0123456789abcdef0123456789abcdef
dataset_code=ROAD
layer_name=道路
load_type=F
crs=EPSG:4490
charset=UTF-8
feature_count=12000
data_time=20261122
increment_mode=
remark=
```

示例中的 `md5` 只演示「32 位十六进制」这种写法，不是该文件的真实指纹。

MD5 约定：

- 算法为 MD5，结果写成 32 位十六进制。
- 建议使用小写。本方比较前会把双方结果都转为小写，大写同样有效。
- 计算对象是上传完成的 zip 文件本身的全部字节。
- 不计算文件名，不计算解压后的 shp、dbf、tif。
- zip 传完再计算。传到一半得到的指纹不能写入清单。
- 本方下载完成后，先比对 `file_size`，再自行计算 MD5，与清单中的 `md5` 比较。

两边指纹不一致时，原因只可能是算的字节范围不同，或文件在传输中不完整。语言不同不会导致指纹不同。

### 2.5 全量与增量

- `F`：本方用该包替换该图层的当前版本。
- `C`：只用于 SHP 等矢量。清单必须填写 `increment_mode`。要素必须带双方已约定的稳定要素标识。`UPSERT` 按标识新增或更新，`DELETE` 按标识逻辑删除，`MIXED` 在要素属性中再带 `I`、`U`、`D`。
- 增量包缺少要素标识，或清单没有 `increment_mode` 时，本方不入库，回执为失败，等待平台重传。

要素标识的字段名按矢量图层在第 4 节登记，发布后不修改。

DEM 高程使用 GeoTIFF，按全量交付。一幅 DEM 是约定范围内的完整高程格网，格网点没有可逐条增删的要素标识，装载标记固定为 `F`。高程有修订时，平台重新投递这一幅完整影像，本方用新影像替换该图层的当前版本。

范围很大、需要按图幅拆开时，每一幅仍是该图幅范围内的完整格网，各自以 `F` 投递。更新哪一幅，就整幅替换哪一幅。

### 2.6 本方处理与回执

处理顺序：

1. 看到同名的 zip、清单、`.ok` 均存在。
2. 读取清单。
3. 下载 zip，比对字节数。
4. 计算 MD5，与清单比较（忽略大小写）。
5. 字节数或 MD5 不一致：不入库，回执失败。
6. 一致后解压。矢量核验 `.prj`、`.cpg` 与清单一致。栅格核验包内有一幅 tif，且文件内坐标系与清单 `crs` 一致。不符则回执 `PARSE_ERROR`，不替换当前版本。
7. 矢量按 2.5 做全量替换或增量合并，按要素标识幂等写入。DEM 等高程栅格用新影像替换该图层当前版本，影像按文件归档，台账登记图层、数据日期、路径、坐标系和 zip 的 MD5。
8. 向 `receipt` 目录写入同名回执。处理成功后，把文件名和 MD5 记入台账。

回执文件名：`{名称}_{装载}_{周期}_{日期}_{时间}.receipt.txt`

回执同样是 UTF-8 的 `键=值`：

```text
file_name=道路_F_D_20261122_020000.zip
md5=0123456789abcdef0123456789abcdef
result=SUCCESS
receive_time=2026-11-22 03:10:00
load_count=12000
remark=
```

`result` 取值：

| 值 | 含义 |
| --- | --- |
| `SUCCESS` | 已入库，`load_count` 为入库要素数 |
| `MD5_MISMATCH` | 字节数或 MD5 与清单不符，未入库 |
| `PARSE_ERROR` | 文件打不开、缺套件、坐标系或字符集与清单不符，未入库 |
| `REJECTED` | 增量包缺少要素标识或 `increment_mode`，未入库 |

矢量全量包的 `load_count` 与清单 `feature_count` 一致后记 `SUCCESS`。两边条数不一致时，在 `remark` 写明两侧条数。栅格清单的 `feature_count` 为 `0`，回执 `load_count` 填 `1`，表示这一幅影像已成为当前版本。

平台以回执作为该包的对账结果。`MD5_MISMATCH`、`PARSE_ERROR`、`REJECTED` 由平台修正后按新时间重传。

## 3. 双方都要遵守的处理规则

- 同一业务主键、同一要素标识重复到达时，使用方只保留一份有效数据。
- 使用方处理成功之后才推进库表水位，或才把文件记入已处理台账。
- 失败批次和失败文件保留原包，用新批次或新时间重传。
- 条数以对账表的 `row_count`、`consume_count`，或清单的 `feature_count`、回执的 `load_count` 为准。
- 对接账号的口令不写入文档、代码仓库和清单文件。

### 4.2 SFTP 文件

| 编号 | 核对项 | 本文约定 | 确认 |
| --- | --- | --- | --- |
| F1 | 协议 | SFTP，二进制 | |
| F2 | 目录 | `incoming` 平台写、使用方读；`receipt` 使用方写、平台读 | |
| F3 | 投递文件 | 同名 zip、`.manifest.txt`、`.ok`，`.ok` 最后上传 | |
| F4 | 命名 | `{名称}_{F或C}_{周期}_{yyyyMMdd}_{HHmmss}` | |
| F5 | 一个包的范围 | 一个 zip 一个图层 | |
| F6 | 包内目录 | `空间数据/`、`数据说明/` | |
| F7 | SHP | `.shp` `.shx` `.dbf` `.prj` `.cpg` 成套，主文件名相同 | |
| F8 | 清单格式 | UTF-8，一行一个 `键=值` | |
